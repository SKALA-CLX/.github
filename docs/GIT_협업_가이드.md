# CLX Git 협업 가이드

> 이 문서는 기존 팀 Git 가이드를 바탕으로 정리한 공통 협업 기준입니다. 팀이 추가로 합의해야 할 내용은 **제안** 또는 **확인 필요**로 표시합니다. GitHub가 자동으로 규칙을 강제하고 있다는 뜻은 아닙니다.
>
> 현재 준비 중인 CI와 배포 흐름은 [CI·배포 준비 가이드](CI_CD_가이드.md)를 함께 확인하세요.

## 1. 전체 흐름

기능과 오류 수정은 Issue에서 시작하고, 최신 `develop`에서 작업 브랜치를 만듭니다. 작업 내용과 확인 결과를 PR로 공유한 뒤 팀원의 리뷰를 거쳐 병합합니다.

```text
기능·오류 Issue 작성
  → 최신 develop에서 작업 브랜치 생성
  → 작업·검증·커밋·push
  → 작업 브랜치 → develop PR
  → 작성자를 제외한 팀원 1명 이상 승인
  → Squash and merge
  → 통합 확인 후 develop → main 별도 PR
  → 작성자를 제외한 팀원 1명 이상 승인
  → Create a merge commit
```

- `develop`은 팀의 작업을 모으는 브랜치, `main`은 검토한 안정 버전과 추후 배포 기준입니다.
- `develop`과 `main`에 직접 push하지 않습니다. `Rebase and merge`와 강제 push는 사용하지 않습니다.
- Issue는 작업의 배경과 완료 기준을 기록하고, PR은 변경을 검토받고 병합을 요청하는 데 사용합니다.
- 문서·설정·CI 작업은 논의나 추적이 필요할 때 Issue를 만듭니다.
- 코드가 아직 없는 저장소도 같은 리뷰 흐름을 따릅니다. 검증할 기능이 없으면 빈 테스트로 성공을 표시하지 말고 PR에 준비 상태와 미검증 사유를 적습니다.

조직의 `.github` 저장소는 현재 `develop` 없이 `main`만 사용하므로 공통 문서 변경은 작업 브랜치에서 `main`을 대상으로 PR을 열어 리뷰합니다. 이 예외는 다른 저장소에 자동으로 적용되지 않습니다.

## 2. 작업 브랜치 이름

기능·오류 수정은 해당 저장소에서 발급받은 **실제 Issue 번호**를 사용합니다. 아래 번호는 예시입니다.

| 작업 | 형식 | 예시 |
| --- | --- | --- |
| 기능 | `feature/<이슈번호>-<설명>` | `feature/12-sensor-list` |
| 오류 수정 | `fix/<이슈번호>-<설명>` | `fix/18-sensor-error` |
| 문서 | `docs/<설명>` | `docs/setup-guide` |
| 설정·기타 | `chore/<설명>` | `chore/update-config` |
| CI | `ci/<설명>` | `ci/backend-checks` |

`feature/`는 브랜치의 접두어이고, 아래 `feat:`는 커밋 또는 PR 제목의 타입입니다. 용도가 서로 다릅니다. 기존 브랜치 이름을 이 안내만으로 일괄 변경하지 않습니다.

**제안:** 설명은 목적을 알 수 있도록 짧게 작성하고, 서로 관계없는 작업은 별도 브랜치로 나눕니다. 자동화 봇 브랜치나 긴급 수정 절차의 예외는 도입 전에 팀이 따로 정합니다.

## 3. 커밋 메시지와 PR 제목

커밋 제목과 PR 제목은 다음 기본 형식을 사용합니다.

```text
타입: 변경 내용
```

```text
feat: 센서 목록 조회 기능 추가
fix: 센서 상세 조회 오류 수정
```

`feat`는 기능 추가, `fix`는 오류 수정을 뜻합니다. `docs`, `test`, `refactor`, `ci`, `chore` 등 추가 타입은 사용 사례를 위한 **제안**이며 고정된 전체 허용 목록은 팀에서 확정하지 않았습니다. 제목 길이, scope, 커밋 제목의 Issue 번호를 별도로 강제하기로 한 합의도 없습니다.

현재 준비된 제목 검사 초안은 PR 제목과 비병합 작업 커밋 제목에서 기본 `타입: 변경 내용` 형식을 확인합니다. 검사 초안은 각 저장소의 PR에서 검토 중이므로 기준 브랜치에 병합되기 전까지 모든 PR에서 실행된다고 가정하지 않습니다. 검사 결과와 병합 차단은 별개입니다. Squash 병합 화면에서 최종 커밋 제목을 수동으로 바꿀 수 있으므로 병합하는 사람도 확인합니다.

## 4. Issue 작성과 PR 연결

### 기능·오류 Issue

- **기능:** 필요한 배경, 할 일, 완료 기준을 적습니다.
- **오류:** 발생 환경과 재현 순서, 기대한 결과와 실제 결과, 해결 확인 기준을 적습니다.
- 문서·설정·CI Issue는 작업을 추적하거나 논의할 필요가 있을 때 만듭니다.
- 화면이나 로그를 첨부하기 전 비밀번호·키·토큰·개인정보를 제거합니다.

### 연결 시 주의

PR에서 관련 Issue를 식별할 수 있게 실제 번호를 적습니다. 예를 들어 `관련 Issue: #12` 또는 자동 종료를 의도할 때 `Closes #12`를 사용할 수 있습니다.

**자동 종료는 PR의 대상과 저장소 기본 브랜치, 설정에 영향을 받습니다.** `Closes #12`를 썼다는 이유만으로 `develop` 병합 시 항상 닫힌다고 가정하지 말고 각 저장소에서 병합 후 확인합니다. 다른 저장소의 Issue는 필요한 경우 `Closes 조직/저장소#번호` 형태를 사용합니다. [GitHub: PR과 Issue 연결](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)

## 5. PR 작성과 리뷰

PR 본문에는 최소한 다음을 남깁니다.

1. **작업 내용과 이유:** 무엇을 왜 변경했는지
2. **관련 Issue:** 기능·오류 작업의 실제 Issue 번호, 또는 해당 없음
3. **확인 방법과 결과:** 실행한 빌드·테스트와 결과
4. **미확인 사항:** 아직 코드·환경이 없거나 실행하지 못한 검사와 이유
5. **리뷰 중점:** 영향 범위와 팀원이 특히 확인할 부분

리뷰어는 다음을 확인합니다.

- [ ] PR 대상 브랜치와 변경 파일이 작업 목적에 맞습니다.
- [ ] 작업 내용, Issue와 실제 변경이 서로 맞습니다.
- [ ] 실행한 검사 결과와 실행하지 못한 이유가 정확히 적혀 있습니다.
- [ ] 기존 기능·설정에 미치는 영향을 검토했습니다.
- [ ] 코드·문서·화면·로그에 비밀번호, 키, 토큰, 개인정보가 없습니다.

작업 브랜치에서 `develop`으로의 PR은 **Squash and merge**하고, 통합 확인 후 `develop`에서 `main`으로 별도 PR을 열어 **Create a merge commit**을 사용합니다. 두 PR 모두 작성자가 아닌 팀원 1명 이상의 승인을 받습니다. 작업 브랜치는 남은 작업을 확인한 뒤 정리하며 `develop`과 `main`은 유지합니다.

## 6. 처음부터 따라 하기

아래 번호와 파일 경로는 예시입니다. 해당 저장소에서 발급된 Issue 번호와 실제 변경 파일을 사용하세요.

1. 기능 또는 오류 Issue를 만들고 번호를 확인합니다.
2. 저장소 폴더에서 변경 중인 파일을 확인합니다. 기존 변경이 있다면 임의로 버리지 않습니다.

```bash
git status
git switch develop
git pull --ff-only origin develop
git switch -c feature/12-sensor-list
```

`develop`이 없거나 `--ff-only` 갱신이 실패하면 강제로 진행하지 말고 저장소 담당자에게 현재 상태를 확인합니다.

3. 실제 작업을 하고 가능한 검사를 실행합니다. `git status`와 `git diff`로 의도하지 않은 변경이나 비밀이 섞이지 않았는지 확인합니다.
4. 필요한 파일을 선택해 커밋하고 작업 브랜치에 올립니다.

```bash
git add -- 실제/변경한/파일
git commit -m "feat: 센서 목록 조회 기능 추가"
git push -u origin feature/12-sensor-list
```

5. GitHub에서 받는 브랜치(base)가 `develop`인지 확인하고 PR을 작성합니다. 리뷰를 요청하고 검사 결과를 확인합니다.
6. 팀 승인 후 작업 브랜치 → `develop`은 squash로 병합합니다. 이후 별도 `develop` → `main` PR을 리뷰하고 merge commit으로 병합합니다.

## 7. 자동 적용 및 보호 상태

- 이 가이드는 **팀의 협업 기준**입니다. 읽는 것만으로 리뷰 승인, 직접 push 금지 또는 CI 통과가 GitHub에서 자동 강제되지는 않습니다.
- GitHub 브랜치 보호·Ruleset의 지원 여부와 적용 상태는 저장소 및 조직 설정을 따로 확인합니다. 적용되기 전에는 팀이 PR 검사와 리뷰를 직접 확인합니다.
- 이 조직의 `.github` 저장소는 현재 비공개이므로, 일반 조직의 GitHub 기본 커뮤니티 파일 상속 조건을 충족한다고 가정하지 않습니다. Issue·PR 템플릿을 각 저장소에 어떻게 적용할지는 팀에서 결정합니다. [GitHub: 기본 커뮤니티 파일](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/creating-a-default-community-health-file)
- 조직 `.github`에 공통 문서나 워크플로를 둔다고 각 저장소의 CI가 자동 실행되지는 않습니다. 재사용 워크플로는 각 저장소의 호출 및 접근 설정이 필요합니다.
- 기능 PR의 이슈 연결, 추가 타입, 템플릿 필수 항목, 자동화 봇 브랜치 예외와 보호 정책은 팀이 합의한 뒤 갱신합니다.

**이 문서와 모든 저장소에 비밀번호, API 키, 토큰 또는 개인정보를 기록하지 않습니다.**
